Installation sur un VPS Debian

Mise en production de la couche de diffusion — Meilisearch, API, client web et fichiers audio — sur un serveur Debian 12 (bookworm). Omeka S, la base source, n'a pas besoin d'être sur ce serveur.

1Prérequis

  • Un VPS Debian 12, accès sudo ou root.
  • Un nom de domaine pointé vers l'IP du VPS — nécessaire pour le HTTPS, et donc pour la reconnaissance vocale du navigateur, qui exige une origine sécurisée.
  • Soit un accès réseau depuis le VPS vers la base MySQL/MariaDB d'Omeka S, soit les artefacts déjà générés ailleurs (audios/, data/, un export Meilisearch) à transférer — voir §5.

2Préparation du système

sudo apt update && sudo apt full-upgrade -y
sudo apt install -y python3 python3-venv python3-pip ffmpeg git curl rsync apache2 ufw

Compte système dédié, sans shell de connexion — l'app ne doit pas tourner en root :

sudo useradd --system --create-home --home-dir /opt/flux-conceptuel-auto \
  --shell /usr/sbin/nologin fluxconceptuel

Pare-feu minimal : seuls SSH, HTTP et HTTPS sont exposés. Meilisearch (7700) et l'API (8000) restent en écoute sur 127.0.0.1 uniquement.

sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable

3Installation de Meilisearch

curl -L https://install.meilisearch.com | sh
sudo install -m 0755 ./meilisearch /usr/local/bin/meilisearch
sudo mkdir -p /var/lib/meilisearch
sudo chown fluxconceptuel:fluxconceptuel /var/lib/meilisearch
Important

En développement local le projet tourne sans clé Meilisearch, ce qui n'est acceptable que sur 127.0.0.1. En production, sans clé, n'importe qui atteignant le port pourrait lire ou effacer tout l'index.

openssl rand -base64 48
# gardez cette valeur : elle sert deux fois, ci-dessous et dans le .env de l'API (§5)

/etc/systemd/system/meilisearch.service :

[Unit]
Description=Meilisearch
After=network.target

[Service]
Type=simple
User=fluxconceptuel
Group=fluxconceptuel
Environment=MEILI_MASTER_KEY=REMPLACER_PAR_LA_CLE_GENEREE
Environment=MEILI_ENV=production
WorkingDirectory=/var/lib/meilisearch
ExecStart=/usr/local/bin/meilisearch --db-path /var/lib/meilisearch --http-addr 127.0.0.1:7700 --no-analytics --dump-dir /var/lib/meilisearch/dumps --snapshot-dir /var/lib/meilisearch/snapshots
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now meilisearch
sudo systemctl status meilisearch   # doit être "active (running)"
Si le service échoue avec Permission denied (os error 13)

Meilisearch crée dumps/ et snapshots/ dans son répertoire de travail : d'où le WorkingDirectory et les chemins --dump-dir/--snapshot-dir ci-dessus. Si vous placez le --db-path ailleurs que /var/lib/meilisearch (autre disque, /mnt/…), adaptez ces trois chemins et assurez-vous que fluxconceptuel possède le dossier et peut traverser tous ses parents (namei -l <chemin> pour vérifier, chown -R fluxconceptuel:fluxconceptuel sur le dossier Meilisearch).

4Déploiement du code

Le dépôt (github.com/samszo/exploDeleuze) est un monorepo — Flux Conceptuel Auto vit dans le sous-dossier exploreConceptsInCar/, à côté d'autres projets sans rapport. On clone le dépôt entier puis on fait pointer app/ vers le bon sous-dossier :

sudo -u fluxconceptuel git clone https://github.com/samszo/exploDeleuze.git /opt/flux-conceptuel-auto/repo
sudo -u fluxconceptuel ln -s /opt/flux-conceptuel-auto/repo/exploreConceptsInCar /opt/flux-conceptuel-auto/app
Si /opt/flux-conceptuel-auto/app est introuvable

Soit cette étape n'a pas encore été exécutée, soit le dépôt a été cloné sans le lien symbolique — l'app se trouve alors dans /opt/flux-conceptuel-auto/repo/exploreConceptsInCar/, pas directement dans repo/. Le reste de ce guide suppose que app/ pointe (clone direct ou via ce lien) sur le dossier qui contient api/, web/, scripts/, requirements.txt.

(à défaut d'un accès à ce dépôt depuis le VPS, rsync depuis la machine de développement fonctionne tout aussi bien — voir la commande au §5 ; dans ce cas, rsyncez directement vers /opt/flux-conceptuel-auto/app/, pas besoin du lien symbolique)

cd /opt/flux-conceptuel-auto/app
sudo -u fluxconceptuel python3 -m venv .venv
sudo -u fluxconceptuel ./.venv/bin/pip install -r requirements.txt
sudo -u fluxconceptuel ./.venv/bin/pip install gunicorn
Ne jamais copier .venv/ ni .env depuis la machine de dev

Un environnement virtuel n'est pas portable : ses binaires et extensions compilées sont liés à l'OS, l'architecture et la version de Python de la machine où il a été créé. Un .venv rsyncé d'un Mac vers le VPS produit des erreurs status=203/EXEC sur gunicorn (binaires Mach-O au lieu d'ELF). Si vous synchronisez le code par rsync, excluez ces deux entrées (--exclude .venv --exclude .env) et recréez-les sur le VPS : .venv avec les commandes ci-dessus, .env avec le bloc tee plus bas. Pour repartir propre : sudo rm -rf .venv (en root, pas en fluxconceptuel — les fichiers copiés appartiennent souvent à un autre utilisateur).

Erreur error: externally-managed-environment ?

Debian bloque volontairement pip install sur le Python système (PEP 668). Ce n'est jamais l'appel ./.venv/bin/pip ci-dessus qui la déclenche — c'est un pip install tapé sans ce préfixe, donc sur le pip système. Ne contournez pas avec --break-system-packages : vérifiez plutôt que .venv/ existe (ls .venv/bin/pip) et rejouez la commande telle quelle. Si .venv/bin/pip est absent après python3 -m venv .venv, le paquet python3-venv manque (sudo apt install python3-venv, puis recréez le venv).

Activer le venv plutôt que préfixer chaque commande. Ce guide préfixe systématiquement par ./.venv/bin/ parce que chaque sudo -u fluxconceptuel <commande> ouvre un shell séparé et non interactif — une activation ne survivrait pas d'une commande à l'autre. Pour une session de travail manuelle plus longue (par exemple pour rejouer le pipeline de la §5), ouvrez plutôt un vrai shell sous cet utilisateur et activez une fois pour toute la session :

sudo -u fluxconceptuel -s
cd /opt/flux-conceptuel-auto/app
source .venv/bin/activate   # le prompt affiche (.venv) ; plus besoin de préfixer ensuite
./scripts/export_manifest.sh
./scripts/convert_batch.sh
python3 scripts/mine_concept_phrases.py
python3 scripts/export_meilisearch.py
exit                        # quitte le shell fluxconceptuel (désactive au passage)

Les services systemd (§6) n'ont besoin d'aucune activation : ExecStart appelle directement le binaire du venv (.venv/bin/gunicorn), sans passer par un shell interactif.

Créez le .env (jamais commité — permissions restrictives) :

sudo -u fluxconceptuel tee .env > /dev/null <<'EOF'
MEILI_URL=http://127.0.0.1:7700
MEILI_KEY=REMPLACER_PAR_LA_CLE_GENEREE
OUT_DIR=/opt/flux-conceptuel-auto/app/audios

# signalements de la PWA (§B) — laisser vide pour désactiver la fonction
GOOGLE_CLIENT_ID=
SIGNAL_DIR=/opt/flux-conceptuel-auto/app/signalements
SIGNAL_EXPORT_KEY=REMPLACER_PAR_UNE_CHAINE_ALEATOIRE

# uniquement nécessaire si le pipeline d'export tourne sur CE serveur (§5, option A)
DB_HOST=
DB_USER=
DB_PASS=
DB_NAME=
SRC_ROOT=
EOF
sudo chmod 600 .env

OUT_DIR (lu par l'API comme StaticFiles(directory=...)) et tous les chemins du .env sont des chemins sur le VPS — si vous partez d'un .env de dev, remplacez chaque chemin. Un chemin qui n'existe pas fait planter flux-api au démarrage (RuntimeError: Directory '...' does not exist). MEILI_KEY doit être identique à la MEILI_MASTER_KEY du service Meilisearch (§3).

5Où vivent les données (source vs diffusion)

Omeka S reste la source de vérité et n'a pas besoin d'être sur ce VPS. Deux façons de peupler la couche de diffusion :

Option A — le pipeline tourne sur le VPS

Le VPS a un accès réseau à la base MySQL/MariaDB d'Omeka S (renseignez DB_* et SRC_ROOT dans le .env) :

cd /opt/flux-conceptuel-auto/app
sudo -u fluxconceptuel ./scripts/export_manifest.sh
sudo -u fluxconceptuel ./scripts/convert_batch.sh
sudo -u fluxconceptuel ./.venv/bin/python3 scripts/mine_concept_phrases.py
sudo -u fluxconceptuel ./.venv/bin/python3 scripts/export_meilisearch.py

Option B — les artefacts sont générés ailleurs

Par exemple sur la machine de développement, puis transférés :

rsync -avz --progress audios/ deploy@vps:/opt/flux-conceptuel-auto/app/audios/
rsync -avz --progress data/   deploy@vps:/opt/flux-conceptuel-auto/app/data/

Puis, sur le VPS (Meilisearch démarré, base joignable au moins le temps de cet export) :

sudo -u fluxconceptuel ./.venv/bin/python3 scripts/export_meilisearch.py

Alternative plus rapide si la base n'est pas joignable depuis le VPS : copier directement le répertoire de données Meilisearch déjà construit (service arrêté des deux côtés pendant la copie) :

sudo systemctl stop meilisearch          # sur le VPS
rsync -avz --progress meilisearch/data/ deploy@vps:/var/lib/meilisearch/
sudo chown -R fluxconceptuel:fluxconceptuel /var/lib/meilisearch
sudo systemctl start meilisearch

6Service systemd pour l'API

En production, gunicorn pilotant des workers uvicorn est plus robuste qu'un simple uvicorn --reload — relance automatique en cas de crash, plusieurs workers en parallèle.

/etc/systemd/system/flux-api.service :

[Unit]
Description=Flux Conceptuel Auto — API
After=network.target meilisearch.service
Requires=meilisearch.service

[Service]
Type=simple
User=fluxconceptuel
Group=fluxconceptuel
WorkingDirectory=/opt/flux-conceptuel-auto/app
EnvironmentFile=/opt/flux-conceptuel-auto/app/.env
ExecStart=/opt/flux-conceptuel-auto/app/.venv/bin/gunicorn api.main:app \
  -k uvicorn.workers.UvicornWorker -w 2 --bind 127.0.0.1:8000 \
  --access-logfile - --error-logfile -
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

Ajustez -w 2 (nombre de workers) selon les cœurs disponibles — 2 suffisent largement pour ce trafic.

sudo systemctl daemon-reload
sudo systemctl enable --now flux-api
sudo systemctl status flux-api

7Apache et HTTPS

Pour la performance, Apache sert directement les fichiers statiques (client web et fichiers audio) — bien plus efficace qu'un serveur ASGI Python pour ça — et ne proxifie que les appels /api/. Les requêtes Range (avance rapide dans l'audio) sont supportées nativement par Apache pour les fichiers statiques, sans module supplémentaire.

Activez les modules nécessaires — proxy/proxy_http pour le reverse-proxy vers l'API, headers pour les en-têtes de cache, ssl pour le HTTPS :

sudo a2enmod proxy proxy_http headers ssl

/etc/apache2/sites-available/flux-conceptuel-auto.conf :

<VirtualHost *:80>
    ServerName flux.exemple.tld
    DocumentRoot /opt/flux-conceptuel-auto/app/web

    ProxyPreserveHost On
    ProxyPass /api/ http://127.0.0.1:8000/api/
    ProxyPassReverse /api/ http://127.0.0.1:8000/api/

    Alias /audio/ /opt/flux-conceptuel-auto/app/audios/
    <Directory /opt/flux-conceptuel-auto/app/audios/>
        Require all granted
        Header set Cache-Control "public, max-age=31536000, immutable"
    </Directory>

    <Directory /opt/flux-conceptuel-auto/app/web/>
        Require all granted
    </Directory>

    # PWA hors-ligne (web/app/, servie sur /app/) : type MIME du manifeste
    # et pas de cache sur le service worker
    AddType application/manifest+json .webmanifest
    <Files sw.js>
        Header set Cache-Control "no-cache"
    </Files>

    ErrorLog ${APACHE_LOG_DIR}/flux-conceptuel-error.log
    CustomLog ${APACHE_LOG_DIR}/flux-conceptuel-access.log combined
</VirtualHost>
sudo a2ensite flux-conceptuel-auto
sudo a2dissite 000-default   # évite un conflit avec le site par défaut
sudo apache2ctl configtest && sudo systemctl reload apache2
HTTPS nécessaire

Sans HTTPS, les navigateurs refusent le micro sur une origine autre que localhost — la reconnaissance vocale du client sera bloquée de toute façon.

sudo apt install -y certbot python3-certbot-apache
sudo certbot --apache -d flux.exemple.tld

certbot crée automatiquement le VirtualHost 443 correspondant (SSLEngine on et chemins de certificat) et programme le renouvellement automatique (vérifiez avec sudo systemctl status certbot.timer).

Après certbot : reporter ProxyPass et Alias dans le VHost :443

certbot duplique le VHost :80 vers un fichier ...-le-ssl.conf mais ne garantit pas que toutes les directives suivent. Vérifiez que le VHost *:443 contient bien DocumentRoot .../web, les blocs ProxyPass /api/ + ProxyPassReverse, l'Alias /audio/ et son <Directory> — sinon / renvoie Forbidden et /api/ un 404. Deux détails qui mordent : utilisez http://127.0.0.1:8000/ et non http://localhost:8000/ dans ProxyPass (localhost peut résoudre en ::1 alors que gunicorn n'écoute qu'en IPv4 → 502/503) ; et si vous posez un RequestHeader set X-Forwarded-Proto, mettez "https", pas "http".

10Sécurité — récapitulatif

  • Meilisearch (7700) et l'API brute (8000) écoutent sur 127.0.0.1 uniquement ; seul Apache (80/443) est exposé au pare-feu.
  • Clé maîtresse Meilisearch obligatoire en production.
  • .env en permissions 600, jamais commité.
  • L'app tourne sous un compte système dédié sans shell, pas en root.
  • HTTPS obligatoire — sans quoi la reconnaissance vocale sera bloquée par le navigateur.

AAnnexe — pile locale sur macOS

Variante pour faire tourner toute la couche de diffusion (Meilisearch + API + client web) sur son Mac — pour développer, prévisualiser ou tester avant de pousser sur le VPS. Pas de systemd, pas de reverse-proxy, pas de HTTPS : on lance deux processus au premier plan et on ouvre http://localhost:8000/. L'API sert elle-même web/ à la racine (voir api/main.py), donc une seule adresse, même origine, aucun CORS à gérer.

A.1 — Prérequis

brew install meilisearch python@3.13 ffmpeg   # ffmpeg seulement si le pipeline audio tourne ici

A.2 — Code, venv, dépendances

git clone https://github.com/samszo/exploDeleuze.git
cd exploDeleuze/exploreConceptsInCar
python3 -m venv .venv
./.venv/bin/pip install -r requirements.txt

gunicorn est inutile ici : en local on utilise le serveur de développement uvicorn --reload.

A.3 — .env (chemins de ce Mac, en absolu)

tee .env > /dev/null <<EOF
MEILI_URL=http://127.0.0.1:7700
MEILI_KEY=
OUT_DIR=$(pwd)/audios

# uniquement si le pipeline d'export tourne sur ce Mac (§5, option A)
DB_HOST=
DB_USER=
DB_PASS=
DB_NAME=
SRC_ROOT=
EOF

MEILI_KEY reste vide : sans clé, Meilisearch n'est acceptable que sur 127.0.0.1 (voir l'encadré du §3) — ce qui est exactement le cas ici.

A.4 — Peupler les données

Comme au §5. Soit le pipeline complet (accès à la base Omeka S requis, DB_* + SRC_ROOT renseignés) :

source .venv/bin/activate
./scripts/export_manifest.sh
./scripts/convert_batch.sh
python3 scripts/mine_concept_phrases.py
python3 scripts/export_meilisearch.py

Soit, si audios/ et data/ sont déjà là (générés ailleurs), seulement l'export vers Meilisearch — Meilisearch doit tourner (A.5) :

./.venv/bin/python3 scripts/export_meilisearch.py

A.5 — Lancer la pile (deux terminaux)

Terminal 1 — Meilisearch (laisser tourner) :

cd exploDeleuze/exploreConceptsInCar
meilisearch --db-path ./meilisearch/data --http-addr 127.0.0.1:7700 --no-analytics

Terminal 2 — l'API (laisser tourner) :

cd exploDeleuze/exploreConceptsInCar
./.venv/bin/uvicorn api.main:app --reload --port 8000

Puis ouvrir http://localhost:8000/ — le client web, la recherche, la lecture audio et la topologie fonctionnent. --reload redémarre l'API à chaque modification de api/. Découverte des endpoints : http://localhost:8000/docs.

Reconnaissance vocale et accès depuis un téléphone

La reco vocale du navigateur exige une origine sécurisée : elle marche sur http://localhost:8000/ (traité comme sûr) mais pas sur http://<ip-du-mac>:8000/ depuis un autre appareil. Pour tester depuis un téléphone avec le micro, il faut du HTTPS — utilisez la vraie mise en production (VPS), ou ajoutez localement un reverse-proxy à certificat de confiance (Caddy, ou mkcert + Apache/nginx) devant le port 8000.

Ne pas réutiliser ce .venv / .env sur le VPS

Le .venv créé ici est spécifique à macOS (binaires Mach-O) et provoquera status=203/EXEC sur le serveur ; le .env contient des chemins /Users/.... Sur le VPS, recréez les deux (voir §4). Si vous synchronisez par rsync : --exclude .venv --exclude .env.

BAnnexe — l'application hors-ligne (PWA)

web/app/ est une Progressive Web App installable qui télécharge une séance entière (transcriptions + audio) sur le téléphone pour l'écouter et la fouiller sans connexion. Voir web/app/README.md pour le détail fonctionnel.

B.1 — Rien de spécial à installer

Ce sont des fichiers statiques dans web/app/, or web/ est déjà le DocumentRoot (§7). Après un git pull sur le VPS, l'app est servie sur https://<domaine>/app/. Elle cible l'API de la même origine — pas de configuration, pas de CORS.

B.2 — Réglages Apache

Dans le VirtualHost :443 : type MIME du manifeste, et revalidation systématique de la coquille (petits fichiers, l'ETag évite le re-téléchargement inutile — mais le navigateur revérifie à chaque fois, donc un déploiement est vu immédiatement) :

AddType application/manifest+json .webmanifest
<Directory /opt/flux-conceptuel-auto/app/web/app/>
    Require all granted
    Header set Cache-Control "no-cache"
</Directory>
sudo a2enmod headers
sudo apache2ctl configtest && sudo systemctl reload apache2

Sans le type MIME, Chrome ignore le manifeste (l'app reste utilisable mais non « installable »). Le no-cache sur tout web/app/ (couplé à la stratégie « réseau d'abord » du service worker) garantit qu'un git pull est visible au rechargement suivant, sans purge manuelle.

Un ancien service worker sert encore l'ancienne version ?

Symptômes : après déploiement, l'app n'est toujours pas installable, ou un nouveau bouton n'apparaît pas. Un vieux service worker (v2) mettait en cache la coquille en cache-first sans jamais la rafraîchir. Le sw.js depuis flux-shell-v6 corrige ça : réinstall en court-circuitant le cache HTTP (cache: 'reload') et stratégie réseau d'abord — couplé au Cache-Control: no-cache Apache sur web/app/, tout déploiement est pris au chargement suivant. Pas de rechargement automatique côté page : une version antérieure forçait un location.reload() sur controllerchange, ce qui bouclait à l'infini après un vidage de cache. Pour un appareil resté bloqué sur une très vieille version : Chrome → réglages du site → Effacer les données, puis rouvrir /app/ (une seule fois).

« Non installable » — icônes PNG requises

Chrome n'affiche « Installer / Ajouter à l'écran d'accueil » que si le manifeste liste au moins une icône PNG 192×192 et une 512×512. Le manifeste ne référence que des PNG (icon-192.png, icon-512.png, icon-maskable-512.png) : Chrome signale une icône SVG de manifeste comme failed to load même quand elle est valide, donc icon.svg ne sert que de favicon HTML. Les screenshot-*.png alimentent la fiche d'installation enrichie (sinon Chrome prévient juste que la « Richer Install UI » ne sera pas disponible — l'app s'installe quand même). Tous régénérables : rsvg-convert -w 512 -h 512 icon.svg -o icon-512.png. Si le manifeste vu par le navigateur ne montre pas les PNG, c'est le service worker qui sert un ancien cache — voir l'encadré ci-dessus.

B.3 — Vérification

curl -sI https://<domaine>/app/ | head -1
# HTTP/2 200
curl -sI https://<domaine>/app/manifest.webmanifest | grep -i content-type
# content-type: application/manifest+json

Puis sur un téléphone : ouvrir /app/ dans Chrome, « Ajouter à l'écran d'accueil », télécharger une séance, activer le mode avion, vérifier lecture + recherche.

Le service worker exige HTTPS

Le démarrage hors-ligne (coquille en cache) ne fonctionne que sur une origine sécurisée : le HTTPS du VPS, ou http://localhost en dev. Sur http://<ip-locale>:8000/app/ l'enregistrement échoue silencieusement — l'app marche en ligne, mais pas hors-ligne. Le téléchargement et la lecture depuis IndexedDB, eux, ne dépendent pas du service worker.

B.4 — Signalements collaboratifs

Connecté (Google pour l'instant), un utilisateur peut signaler depuis le lecteur une correction de transcription ou une référence (personne, œuvre, date, lieu) à un instant précis d'un fragment. L'API n'écrit pas dans Omeka S : chaque signalement devient un fichier JSON dans SIGNAL_DIR, à réimporter plus tard. L'identité (provider + sub + email + name) est conservée pour rattacher ou créer le compte Omeka au moment de l'import.

  • GET /api/auth/providers — fournisseurs activés (la PWA n'affiche que ceux-là)
  • POST /api/signalements — vérifie le jeton auprès du fournisseur, écrit SIGNAL_DIR/<date>-<id>.json. Requiert désormais selection (la séquence de mots du fragment concernée par le signalement), rejeté en 400 sinon.
  • GET /api/signalements/mine?id_token=&provider= — signalements de l'utilisateur connecté (jeton revérifié), pour l'écran « Mes annotations » de la PWA
  • GET /api/signalements/fragment/{id_trans} — signalements existants sur un fragment, publique (aucun jeton), affichés dans le lecteur ; ne renvoie jamais l'e-mail ni l'identifiant du fournisseur, seulement le nom d'affichage
  • GET /api/signalements/export?key=… — tous les signalements en un tableau JSON (protégé par SIGNAL_EXPORT_KEY)

Configuration Google (console Google Cloud → Identifiants → ID client OAuth 2.0, type Application Web) :

  • Origine JavaScript autorisée : https://<domaine>
  • URI de redirection autorisé : https://<domaine>/app/ (exactement — barre oblique finale comprise ; ajoutez http://localhost:8000/app/ pour tester en local)
  • Reportez l'ID client (public, aucun secret nécessaire avec le flux implicit) dans GOOGLE_CLIENT_ID du .env, puis sudo systemctl restart flux-api
ls -ld /opt/flux-conceptuel-auto/app/signalements       # créé au 1er signalement, doit appartenir à fluxconceptuel
curl -s "https://<domaine>/api/signalements/export?key=<SIGNAL_EXPORT_KEY>"   # [] au départ

signalements/ est dans le .gitignore — sauvegardez ce dossier avec le reste (§9).

B.5 — Export Zotero

Le lecteur propose « Enregistrer dans Zotero » : le fragment courant devient un item audioRecording (texte transcrit + fichier .opus en pièce jointe), rattaché à un item « cours » dédupliqué sur le lien catalogue BnF. Rien à configurer côté serveur — l'API Zotero (api.zotero.org) gère le CORS, la PWA l'appelle directement. L'utilisateur saisit une fois son User ID Zotero et une clé API avec droit d'écriture (zotero.org/settings/keys), stockés localement dans le navigateur.
